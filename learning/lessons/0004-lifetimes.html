Lesson 4 — lifetimes

'a is a claim, not a lifespan

Lessons 1–3 gave you the tools: owned values, &, &mut, *. This lesson is about the annotation the compiler sometimes demands on top of those: 'a. The single most important thing to unlearn first:

The misconception to drop
'a does not make anything live longer, and it isn't a runtime value — it's erased before compilation finishes. It's a name you give to a relationship between references so the borrow checker can verify it. You're not controlling lifetimes; you're describing a constraint that already exists in your code, so the compiler can check it instead of guessing.

Why the compiler needs help

fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}

This won't compile. Not because anything is actually wrong at runtime — but because the compiler has to decide, just from the signature, how long the returned reference is allowed to live. Does it borrow from x? From y? It can't tell without looking inside the function body, and Rust deliberately checks function signatures without needing to read the caller's or callee's implementation. So you tell it:

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

Read this as: "there's some lifetime 'a. Both x and y are valid for at least 'a. Whatever I return will also be valid for at least 'a." Since both parameters share the same 'a, the compiler now knows the returned reference can't outlive the shorter-lived of the two inputs — which is exactly true, since the function might return either one.

What this catches at the call site

let string1 = String::from("long string is long");
let result;
{
    let string2 = String::from("xyz");
    result = longest(&string1, &string2);
}   // string2 dropped here
println!("The longest string is '{result}'");   // ERROR

result might hold a reference into string2, which is dead by the time println! runs. The 'a annotation is exactly what lets the compiler catch this — without it having to inline and analyze longest's body at every call site. This is the direct cousin of a Java NullPointerException or a C dangling pointer, except it's a compile error instead of something that ships.

Lifetime elision: why you don't always see 'a

Most functions with references don't need explicit lifetimes — the compiler applies three mechanical rules first, and only asks you to annotate when those rules leave it ambiguous:

  1. Every reference parameter gets its own inferred lifetime.
  2. If there's exactly one input reference lifetime, it's assigned to every output reference.
  3. If one parameter is &self or &mut self, its lifetime is assigned to every output.

longest needed an explicit 'a because it has two input reference lifetimes and rule 2 doesn't apply — the compiler genuinely can't pick one over the other. A function like fn first_word(s: &str) -> &str compiles with zero annotations because rule 2 handles it.

Lifetimes on structs

struct Excerpt<'a> {
    part: &'a str,
}

Same idea, applied to a type instead of a function: an Excerpt can't outlive the string its part field borrows from. The compiler will refuse to let you construct one that would dangle.

Java / Kotlin

No equivalent needed — the GC keeps anything reachable alive, so a reference is never left dangling. The cost is paid at runtime, continuously, by the collector.

Rust

No GC, so the compiler must prove statically that no reference outlives its data. 'a is the vocabulary it needs from you to do that proof. Zero runtime cost once it compiles.
