Smart Pointers · Part 1

Box: Heap Allocation with Ownership

In Java, every object lives on the heap and you use new to create it. In Rust, values live on the stack by default. Box<T> is how you explicitly request heap allocation while keeping Rust's single-ownership rules.

Java

// Always heap-allocated
String s = new String("hello");
List<Integer> list = new ArrayList<>();

// GC manages lifetime
// Reference can be copied freely

Rust

// Stack by default
let s = String::from("hello");
let list = vec![1, 2, 3];

// Explicit heap allocation
let boxed_s = Box::new(s);
// boxed_s owns the heap value
// moves like any owned value

What is Box?

Box<T> is a smart pointer that allocates T on the heap. The Box itself lives on the stack and contains a pointer to the heap data. When the Box goes out of scope, the heap data is deallocated.

let b = Box::new(5);
// Stack: b (pointer) → Heap: 5

println!("{}", b); // prints "5"
// Dereferencing happens automatically

Key difference from Java: Box<T> has single ownership. When you move a Box, you move the ownership of the heap data. No copying the pointer.

let b1 = Box::new(5);
let b2 = b1;
println!("{}", b1); // error: b1 was moved
let b1 = Box::new(5);
let b2 = b1; // b1 moved to b2
println!("{}", b2); // OK: b2 owns the heap data

When to Use Box

Rust defaults to stack allocation because it's faster. Use Box when you specifically need heap allocation:

Why is Stack Faster?

Stack allocation is just moving the stack pointer — one CPU instruction. The memory is already there, contiguous, and cache-friendly.

Heap allocation requires the allocator to:

  • Search for a free block large enough (bookkeeping overhead)
  • Update metadata to mark the block as used
  • Handle fragmentation (small gaps between allocations)
  • Return a pointer to memory that might be scattered across RAM (cache-unfriendly)

In Java, you don't choose — objects always go on the heap and the GC cleans up later. In Rust, you pay for heap allocation only when you explicitly ask for it (Box, Vec, String, etc.).

1. Recursive Types (Most Common)

The compiler needs to know the size of every type at compile time. Recursive types have infinite size without indirection:

enum List {
    Cons(i32, List), // infinitely sized!
    Nil,
}

A Box has known size (one pointer), breaking the infinite recursion:

enum List {
    Cons(i32, Box<List>), // fixed size: i32 + pointer
    Nil,
}

let list = List::Cons(1,
    Box::new(List::Cons(2,
        Box::new(List::Nil))));
// represents: 1 → 2 → Nil
Java Parallel
In Java, class Node { int val; Node next; } works because all object references are pointers anyway. In Rust, you must be explicit: Box<Node> makes next a pointer instead of trying to embed the entire next node inline.

2. Trait Objects

When you want to store a value whose exact type is unknown at compile time:

trait Drawable {
    fn draw(&self);
}

let shapes: Vec<Box<dyn Drawable>> = vec![
    Box::new(Circle { radius: 5 }),
    Box::new(Square { side: 10 }),
];
// Like List<Drawable> in Java, but ownership is clear

3. Large Values

Moving large stack values can be expensive. Box moves just the pointer:

struct HugeData([u8; 1_000_000]);

let big = HugeData([0; 1_000_000]); // 1MB on stack
let moved = big; // copies 1MB

let boxed = Box::new(HugeData([0; 1_000_000])); // 1MB on heap
let moved_box = boxed; // copies 8 bytes (pointer)

Box vs &

When should you use Box<T> vs &T?

  • &T: Borrowing an existing value. No ownership transfer. Cheapest option.
  • Box<T>: Creating a new heap-allocated value you own. Use when stack won't work (recursive types) or when you need to transfer ownership of heap data.
fn use_reference(s: &String) {
    // Borrows s, doesn't own it
    println!("{}", s);
} // s still valid in caller

fn take_ownership(s: Box<String>) {
    // Takes ownership of heap-allocated String
    println!("{}", s);
} // String is dropped here
