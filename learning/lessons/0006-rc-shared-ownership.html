Rc: Shared Ownership via Reference Counting

Box<T> gives you heap allocation with single ownership. But what if multiple parts of your program need to own the same data? Rc<T> (Reference Counted) enables shared ownership by counting how many owners exist and dropping the data when the count reaches zero.

Java

// Multiple references, one object
List<String> list = new ArrayList<>();
List<String> alias1 = list;
List<String> alias2 = list;

// GC tracks references automatically
// Object dies when no references remain

Rust

// Single owner by default
let list = vec![String::from("a")];
let alias1 = list; // list moved
// let alias2 = list; // error!

// Rc for multiple owners
let list = Rc::new(vec![...]);
let alias1 = Rc::clone(&list);
let alias2 = Rc::clone(&list);
// Data lives until all Rc's drop

Why is Rc Needed?

Rust's ownership model enforces single ownership: every value has exactly one owner, and when that owner goes out of scope, the value is dropped. This prevents use-after-free bugs at compile time.

But some data structures need multiple ownership. Classic example: a graph where multiple nodes point to the same node.

struct Node {
    value: i32,
    next: Box<Node>,
}

// Each Node owns the next one
// Can't have two nodes pointing to the same next node!

With Rc<T>, multiple nodes can share ownership of the same next node:

use std::rc::Rc;

struct Node {
    value: i32,
    next: Option<Rc<Node>>,
}

let shared_node = Rc::new(Node { value: 5, next: None });
let node1 = Node { value: 1, next: Some(Rc::clone(&shared_node)) };
let node2 = Node { value: 2, next: Some(Rc::clone(&shared_node)) };
// Both node1 and node2 own shared_node
// shared_node drops when both node1 and node2 drop
Why Not Just Use &?

A reference &T borrows data but doesn't own it. The borrower can't outlive the owner. With Rc<T>, there's no single owner — the data lives as long as any Rc pointing to it still exists.

Use &T when the lifetime relationship is obvious at compile time. Use Rc<T> when ownership needs to be dynamic — determined at runtime by how many owners remain.

How Rc Works: Reference Counting

Rc<T> maintains a count of how many Rc pointers to the same data exist. When you clone an Rc, the count increments. When an Rc drops, the count decrements. When the count reaches zero, the data is deallocated.

use std::rc::Rc;

let a = Rc::new(5);
println!("count: {}", Rc::strong_count(&a)); // 1

let b = Rc::clone(&a);
println!("count: {}", Rc::strong_count(&a)); // 2

{
    let c = Rc::clone(&a);
    println!("count: {}", Rc::strong_count(&a)); // 3
} // c drops here, count decrements to 2

println!("count: {}", Rc::strong_count(&a)); // 2
// When a and b drop, count hits 0 and data is freed
Rc::clone vs .clone()

Rc::clone(&a) is cheap — it increments the count and copies the pointer (8 bytes). It does NOT clone the underlying data.

a.clone() would work but is misleading — in Rust, .clone() usually means "deep copy". Use Rc::clone(&a) to make it explicit you're only bumping the count.

Similarity to Java's Memory Model

Java's garbage collector tracks object reachability. When no references point to an object, the GC eventually reclaims it. Rc<T> does something similar, but at compile time + runtime instead of GC pauses.

Java GCRust Rc<T>
Reference tracking GC scans roots + traces reachability periodically Ref count incremented/decremented as Rc's clone/drop
When is memory freed? When GC runs (non-deterministic timing) Immediately when last Rc drops (deterministic)
Overhead GC pause time + memory overhead for metadata Increment/decrement operations + count storage (one usize per Rc)
Handles cycles? Yes (GC can break cycles via tracing) No (Rc cycle leaks memory — need Weak<T>)
Thread safety Yes (JVM handles it) No (Rc is single-threaded; use Arc for threads)

Key insight: In Java, every object reference is like an invisible Rc. The GC tracks when the "reference count" (reachability) hits zero. In Rust, references (&T) are compile-time-checked borrows, and Rc<T> is the explicit opt-in for Java-like shared ownership.

Rc vs Box: When to Use Each

Both Box<T> and Rc<T> allocate on the heap. The difference is ownership semantics:

  • Box<T>: Single owner. Use when one part of your code owns the data and you need heap allocation (recursive types, trait objects, large values).
  • Rc<T>: Multiple owners. Use when multiple parts of your code need to share ownership of the same data, and it's unclear at compile time which part will drop last.
// Box: single owner
let unique = Box::new(vec![1, 2, 3]);
// let copy = unique; // moves unique, single ownership

// Rc: multiple owners
let shared = Rc::new(vec![1, 2, 3]);
let copy1 = Rc::clone(&shared);
let copy2 = Rc::clone(&shared);
// All three point to the same data
Memory Layout

Box<T>: [stack: pointer] → [heap: T]

Rc<T>: [stack: pointer] → [heap: ref_count + T]

An Rc stores the reference count alongside the data on the heap. Multiple Rc pointers point to the same heap allocation.

Limitation: Immutability by Default

Rc<T> gives you shared ownership, but the data is immutable by default. You can't get a &mut T from an Rc<T> because multiple owners might exist.

let shared = Rc::new(vec![1, 2, 3]);
shared.push(4); // error: cannot borrow as mutable

To mutate shared data, combine Rc<T> with RefCell<T> (interior mutability). We'll cover that in the next lesson.
