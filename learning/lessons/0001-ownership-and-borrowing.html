Lesson 1 — Ownership & the borrow operator

Why &s isn't a Java reference

In Java or Kotlin, every variable holding an object is a reference — a handle to something on the heap that a garbage collector cleans up whenever nothing points to it anymore. You never think about who owns an object; the GC figures that out for you, at runtime, by counting reachability.

Rust has no garbage collector. Instead, every value has exactly one owner — one variable responsible for cleaning it up — decided entirely at compile time. When that owner goes out of scope, Rust inserts the cleanup code right there, with zero runtime tracking. This is the single idea everything else in this lesson (and lessons 2–4) builds on.

Ownership: one variable, one job

fn main() {
    let s1 = String::from("hello");
    let s2 = s1;             // ownership of the String MOVES to s2

    println!("{s1}");        // ERROR: s1 no longer owns anything
}

This is not a copy, and it's not two references to one object like Java's s2 = s1 would be. s1's ownership moved to s2. After the move, s1 is deliberately unusable — the compiler statically rejects the next line. There is no shared mutable object here the way there would be in Java; there is exactly one String, and only one variable is allowed to be responsible for it at a time.

Java / Kotlin

var s2 = s1;
Both variables now point at the same object. Both remain valid. No compiler tracking of who "owns" it — the GC decides when it dies, at runtime.

Rust

let s2 = s1;
Ownership transfers to s2. s1 is now invalid — enforced by the compiler, at compile time, for free at runtime.

The problem: what if you just want to look?

If every function call moved ownership, you'd have to hand a value back out of every function just to keep using it afterward. That's what borrowing solves.

fn main() {
    let s1 = String::from("hello");
    let len = calculate_length(&s1);   // borrow, don't move

    println!("The length of '{s1}' is {len}.");  // s1 still valid
}

fn calculate_length(s: &String) -> usize {
    s.len()
}

&s1 creates a shared reference — a borrow. calculate_length receives a pointer to s1's data but does not own it, so nothing gets dropped when the borrow goes out of scope at the end of the function. Ownership never left main. This is what & means everywhere in Rust: "I'm looking, I don't own this."

The mental model swap
Stop reading &T as "a reference to T" (which is what every Java variable already is). Read it as "a temporary, read-only loan of a value someone else owns." The loan has to end before or when the owner's scope ends — that's what lifetimes (lesson 4) pin down precisely.

Shared borrows can stack

Unlike the mutable case (next lesson), you can have as many &T borrows of the same value as you want at once — because none of them can change it, there's nothing to race:

let s = String::from("hello");
let r1 = &s;
let r2 = &s;
println!("{r1} and {r2}");   // fine — both just reading
