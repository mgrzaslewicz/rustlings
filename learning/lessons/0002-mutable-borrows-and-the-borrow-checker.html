Lesson 2 — &mut and the borrow checker

Exclusive access: &mut

Lesson 1 covered &T: a read-only loan, and you can hand out as many as you like. This lesson covers &mut T: a loan that can also write — and Rust only ever allows one of those to exist at a time, with zero &T alongside it.

The rule

Aliasing XOR mutability
At any given point, for a given value, you may have either any number of &T or exactly one &mut T — never both kinds at once.

This has no equivalent in Java or Kotlin. Any Java reference can always be used to mutate the object it points to, and any number of references can alias the same object while some of them write to it — that's exactly how data races and "who mutated this out from under me" bugs happen in concurrent Java code. Rust's compiler refuses to compile code where that could happen, full stop, before the program ever runs.

Getting one

fn main() {
    let mut s = String::from("hello");
    change(&mut s);
    println!("{s}");   // "hello, world"
}

fn change(some_string: &mut String) {
    some_string.push_str(", world");
}

Two things had to line up: s itself had to be declared mut (you can't mutably borrow something you couldn't mutate directly), and the parameter type is &mut String, not &String.

What the compiler actually rejects

let mut s = String::from("hello");
let r1 = &s;       // shared borrow #1 — fine so far
let r2 = &s;       // shared borrow #2 — still fine, both read-only
let r3 = &mut s;   // ERROR: can't borrow mutably while r1/r2 are alive
println!("{r1}, {r2}, {r3}");

The error isn't arbitrary pedantry — it's preventing a real bug class. If r3 were allowed to mutate s while r1/r2 still expect to read the old value, that's a data race in spirit even in single-threaded code (and a literal one across threads). The borrow checker's job is to make that class of bug a compile error instead of a runtime surprise.

let mut s = String::from("hello");
let r1 = &s;
let r2 = &s;
println!("{r1}, {r2}");   // r1, r2 not used again after this line

let r3 = &mut s;          // fine — r1, r2's borrows already ended
println!("{r3}");

This compiles. A borrow's lifespan ends at its last use, not at the end of the enclosing block — the compiler tracks that precisely (this is the "non-lexical lifetimes" feature, if you want the term for later searching).

Java / Kotlin

Any reference can mutate. Multiple threads mutating the same object concurrently is a runtime bug you find via race conditions, flaky tests, or production incidents.

Rust

Only one mutable path to a value can exist at a time, checked at compile time. The equivalent bug is a compile error, not a 3am page.

Open exercises/06_move_semantics/move_semantics3.rs and move_semantics4.rs — both are fixed by choosing correctly between owned, &, and &mut parameters.

Check yourself

let r1 = &mut s; let r2 = &s; both used below — does this compile?

let r1 = &s; println!("{r1}"); let r2 = &mut s; — does this compile?
